# laya-mcp

[Laya](https://github.com/NandhaKishorM/laya) एक तेज़, नॉन-ऑटोरिग्रेसिव «System 1» निर्णय मॉडल है: यह किसी state पर टाइप किए गए प्रश्न — `noul` (हाँ/नहीं), `choice`, `score` — का उत्तर देता है और एक ही forward pass में प्रायिकताएँ लौटाता है। यह वाकई अच्छा है, और यह एक शोध-परिणाम है।

यह वह हिस्सा है जो इसे सर्वर के संपर्क में टिकाऊ बनाता है।

[English](README.md) · [简体中文](README-zh.md) · [Español](README-es.md) · [Português](README-pt.md) · [हिन्दी](README-hi.md)

```bash
pip install 'laya-mcp[mcp]'
laya-mcp serve            # मॉडल एक बार लोड करता है, 127.0.0.1:8787 पर गर्म रखता है
laya-mcp install          # आपके पास जो भी agent harness हो, उसमें इसे पंजीकृत करता है
```

> **स्थिति: 0.2.2, निर्माणाधीन।** मूल हिस्सा लागू हो चुका है और इसका शुद्ध तर्क 94 जाँचों से ढका है, परंतु इसे CI में किसी वास्तविक harness के विरुद्ध अंत-से-अंत तक नहीं परखा गया। 1.0 से पहले इंटरफ़ेस बदल सकते हैं।

## यह किस समस्या का समाधान है

Laya चुपचाप चीज़ें काट देता है, और ये छूटें उस किस्म की हैं जो गलत उत्तर पर कार्य करने के बाद ही दिखती हैं।

**यह state को अंत से काटता है, और कुछ नहीं बताता।** `build_sequence` विकल्पों के बाद जो जगह बचती है वह state को देता है और उसे `st[:room]` से काट देता है। एक लंबा दस्तावेज़ अपनी पूँछ खो देता है — और किसी अनुबंध, लॉग या ईमेल थ्रेड में उत्तर अक्सर वहीं होता है — फिर मॉडल बचे हुए अग्रभाग पर पूरे भरोसे के साथ उत्तर देता है। उत्तर में इसे दर्शाने वाला कुछ नहीं होता।

**यह विकल्पों को तब तक छोटा करता है जब तक लेबल अलग-अलग पहचाने न जा सकें।** विकल्प एक निश्चित `head_max_len` बजट साझा करते हैं (अंग्रेज़ी checkpoint पर 192 टोकन, बाक़ी पर 256)। एक बिंदु के बाद हर लेबल को ~4 टोकन मिलते हैं। यह Banking77 पतन का प्रलेखित कारण है (0.425, जबकि Jev का 0.870), और यह भी कहीं रिपोर्ट नहीं होता।

**इसका सत्यापन केवल एक जाँच है।** अज्ञात `type` पर `QTYPES[q["t"]]` से नंगा `KeyError` आता है; अनुपस्थित `criteria` भी नंगा `KeyError` है। दोनों मॉडल के bug से अलग नहीं पहचाने जा सकते, और कोई भी दोषी प्रश्न का नाम नहीं बताता।

**इसका `confidence` सटीकता नहीं है।** `choice` और `score` के लिए यह `1 - H(p)/log(k)` है, और `noul` के लिए `max(p, 1-p)`। सामान्यीकृत एंट्रॉपी तब *कम* होती है जब प्रायिकता बिखरी हो — भले ही शीर्ष विकल्प सही हो — और आत्मविश्वास से गलत उत्तर पर *ज़्यादा* होती है: अंग्रेज़ी checkpoint ख्मेर पर 0.952 के confidence पर 0.000 सटीकता पाता है। इस पर सीमा तय करने का अर्थ वह नहीं जो दिखता है।

**और यह चुपचाप CPU पर उतर आता है।** CUDA OOM पर यह मॉडल को fp32 में, वहीं, स्थायी रूप से CPU पर ले जाता है, और stdout पर छापता है। कहीं कोई फ़्लैग सेट नहीं होता। जो प्रक्रिया एक बार यह झेल लेती है वह उत्तर देती रहती है, लगभग 10–15 गुना धीमे, और उत्तर में कुछ भी इसे स्वीकार नहीं करता।

इसलिए यह पैकेज वह जोड़ता है जो छूटा था: एक **preflight** जो बताता है क्या कटेगा, **संरचित त्रुटियाँ** जो प्रश्न का नाम लेती हैं, एक **ईमानदार confidence अनुबंध**, और एक **स्वास्थ्य सतह** जो अवनति की रिपोर्ट करती है।

## यह क्या करता है

| | |
|---|---|
| **गर्म sidecar** | एक `Router`, पूर्व-लोडेड, प्रक्रिया के पूरे जीवनकाल के लिए। Laya का डिफ़ॉल्ट (`max_loaded=1`) हर भाषा-परिवर्तन पर मॉडल दोबारा बनाता है — अपस्ट्रीम मापन: CPU पर 7.4 सेकंड औसत पुनर्लोड, T4 पर 10.3 सेकंड। |
| **टोकन-बजट preflight** | `laya_plan` **मॉडल चलाए बिना** बताता है ठीक क्या काटा जाएगा और हर विकल्प को वास्तव में कितने टोकन मिलते हैं। विकल्पों का गणित `build_sequence` को पंक्ति-दर-पंक्ति दोहराता है। |
| **संरचित त्रुटियाँ** | हर Laya विफलता एक कोड, एक HTTP स्थिति, दोषी प्रश्न id और एक संकेत बन जाती है। `KeyError('ranking')` टाइप बताते हुए `invalid_question` बन जाता है। |
| **ईमानदार confidence** | हर उत्तर में `confidence` को वही कहा जाता है जो वह है। `noul` उत्तरों के साथ `no` / `uncertain` / `yes` बैंड भी आता है, क्योंकि अंशशोधित प्रायिकता निर्णय नहीं होती। |
| **अंशशोधन भंडार** | अपने स्वयं के लेबल किए डेटा पर प्रति `(primitive, विकल्प बकेट)` एक तापमान फ़िट करें, सहेजें, पुनः लोड करें। `laya-multilingual` में **कोई** फ़िट किया तापमान नहीं आता, इसलिए जब तक आप यह न करें इसकी प्रायिकताएँ कच्ची हैं। |
| **डिवाइस ईमानदारी** | चुपचाप हुई CPU अवनति की रिपोर्ट करता है, और `doctor` `torch.cuda.is_available()` पर भरोसा करने के बजाय एक वास्तविक ऑपरेशन चलाकर सिद्ध करता है कि GPU काम करता है। |
| **क्रमबद्ध अनुमान** | डिफ़ॉल्ट रूप से एक lock। Laya थ्रेड-सुरक्षित नहीं है: OOM पर `system_one` `self.device` को पुनः निर्धारित करता है और `self.model.to(...)` कहता है, इसलिए समवर्ती कॉल किसी डिवाइस-स्थानांतरण से टकरा सकते हैं। |
| **पुनर्चक्रणीय** | `DELETE /model` मॉडल छोड़ता है और CUDA allocator cache खाली करता है, जो `Router.unload` नहीं करता। जो मॉडल सर्वर लीक करता है उसे पुनर्चक्रणीय होना चाहिए। |
| **एक `noul` जो स्थिरांक नहीं है** | Laya हर `noul` को `false: ...` / `true: ...` के रूप में प्रस्तुत करता है और फिर लगभग सभी पर «false» कहता है — दोनों भाषाओं में 40 में से 40 मद, ठीक संयोग-स्तर। टूटती लेबल-शब्द है, primitive नहीं, इसलिए boundary वाला `noul` तटस्थ लेबल के साथ दो-विकल्पीय choice के रूप में पूछा जाता है और `P(true)` के रूप में पढ़ा जाता है: उन्हीं चालीस मदों पर **0.500 → 1.000** (अंग्रेज़ी) और **0.975** (बहुभाषी)। boundary रहित `noul` ज्यों का त्यों भेजा जाता है और उत्तर कारण बताता है। |

## एक इंस्टॉलर, छह harness

MCP सर्वर पंजीकृत करने का कोई पोर्टेबल तरीक़ा नहीं है। वास्तव में स्थापित harnesses के विरुद्ध मापने पर वे फ़ाइल, प्रारूप और कुंजी — तीनों में अलग हैं:

| harness | कॉन्फ़िग | प्रारूप | कुंजी |
|---|---|---|---|
| Claude Code | `~/.claude.json` | JSON | `mcpServers` |
| Cursor | `~/.cursor/mcp.json` | JSON | `mcpServers` |
| Codex | `~/.codex/config.toml` | TOML | `[mcp_servers.<name>]` |
| opencode | `~/.config/opencode/opencode.json[c]` | JSON | `mcp` |
| OpenClaw | `~/.openclaw/openclaw.json` | JSON | `mcp.servers` |
| Hermes | `HERMES_HOME`, वरना Windows पर `%LOCALAPPDATA%\hermes` या `~/.hermes` | YAML | `mcp_servers` |

`laya-mcp install` पता लगाता है कि कौन-से मौजूद हैं और हर एक में सही आकार लिखता है। सभी लेखक बदलने के बजाय मिलाते हैं, पहले बैकअप लेते हैं, और ऐसी फ़ाइल को छूने से इनकार करते हैं जिसे वे पढ़ नहीं सकते — `~/.claude.json` इतिहास और प्रति-प्रोजेक्ट स्थिति रखने वाली एक बड़ी साझा फ़ाइल है, और एक निर्णय मॉडल स्थापित करने के लिए उसे मिटा देना एक विनाशकारी सौदा होगा।

दो ईमानदार सीमाएँ:

* **opencode अपनी ही प्रविष्टि के भीतर तीन बार और अलग है**: `command` एक ही array है जिसमें executable *और* उसके आर्ग्युमेंट दोनों होते हैं, environment कुंजी `environment` है `env` नहीं, और टॉगल `enabled` है। वहाँ `disabled: true` लगाना चुपचाप अनदेखा हो जाता है।
* **`pi` समर्थित नहीं है।** यह चूक नहीं है: `pi` में मूल MCP समर्थन नहीं है। उसके settings संदर्भ में कोई MCP कुंजी नहीं है, और MCP के लिए उसका अपना अपस्ट्रीम अनुरोध *«Add MCP extension example»* शीर्षक से है — `pi` में MCP वह extension है जो आप स्वयं बनाते हैं। ऐसी कोई कॉन्फ़िग फ़ाइल नहीं जिसे इंस्टॉलर लिख सके। `install` इसे पहचानता है और बता देता है।

`install` harness को `laya-mcp` कंसोल स्क्रिप्ट के बजाय जानबूझकर `python -m laya_mcp mcp` की ओर इंगित करता है: Windows पर कंसोल स्क्रिप्ट एक `.cmd` शिम होती है और MCP SDK `shell: false` के साथ प्रक्रिया बनाता है, जो उसे चला नहीं सकता।

### Skills

केवल सर्वर पंजीकृत करना आधी स्थापना है। skill के बिना harness को एक-पंक्ति विवरण वाले पाँच उपकरण दिखते हैं, पर वे नियम नहीं दिखते जो तय करते हैं कि उत्तर का कोई अर्थ है या नहीं:

```bash
laya-mcp install --with-skill   # मिले हर harness के लिए MCP पंजीकरण + SKILL.md
laya-mcp install --skill-only   # केवल SKILL.md, सर्वर पंजीकरण नहीं
laya-mcp install --with-skill --harness cursor,claude  # केवल ये दो
laya-mcp install --skill-only --dry-run  # केवल पथ दिखाएँ, कुछ न लिखें
```

सभी harness `<skills>/<name>/SKILL.md` पर मिलते हैं; केवल मूल (root) अलग है:

| harness | skill फ़ाइल |
|---|---|
| Claude Code | `~/.claude/skills/laya/SKILL.md` |
| Cursor | `~/.cursor/skills/laya/SKILL.md` |
| Codex | `$CODEX_HOME/skills/laya/SKILL.md`, वरना `~/.codex/skills/laya/SKILL.md` |
| opencode | `~/.config/opencode/skills/laya/SKILL.md` (`XDG_CONFIG_HOME` को प्राथमिकता) |
| OpenClaw | `~/.openclaw/skills/laya/SKILL.md` |
| Hermes | `~/.hermes/skills/laya/SKILL.md` (`HERMES_HOME` वरना प्लेटफ़ॉर्म डिफ़ॉल्ट, कॉन्फ़िग जैसा ही) |

वही मर्ज/बैकअप अनुबंध लागू होता है जो कॉन्फ़िग लेखक पर लागू होता है, और दोबारा चलाना हर बार नया बैकअप बनाने के बजाय `unchanged` के रूप में रिपोर्ट होने वाला no-op है। स्थापित पाठ भंडार-मूल (repository root) का `SKILL.md` है, जो wheel में भी शामिल है ताकि `pip install` बिना checkout के उसे पढ़ सके; `--skill-source FILE` उसे बदल देता है और `--skill-name NAME` फ़ोल्डर का नाम बदलता है (यह frontmatter के `name` से मेल खाना चाहिए)।

`--project DIR` के साथ, प्रोजेक्ट-स्तरीय skills `DIR/.agents/skills/laya/`, `DIR/.claude/skills/laya/` और `DIR/.cursor/skills/laya/` में लिखी जाती हैं — हर मूल आकार के लिए एक लेखन, क्योंकि `.agents/skills` वह तटस्थ निर्देशिका है जिसे Cursor, Codex, opencode और OpenClaw सभी पढ़ते हैं, जबकि Claude और Cursor अपनी मूल निर्देशिका पसंद करते हैं। Hermes का कोई प्रोजेक्ट skill दायरा नहीं है, इसलिए ऊपर की वैश्विक स्थापना ही उसकी पूरी कहानी है। नई skill दिखने से पहले Cursor को पूरी तरह बंद करके फिर खोलना पड़ता है; Claude Code उसे तुरंत पकड़ लेता है।

## उपकरण

| उपकरण | यह क्या उत्तर देता है |
|---|---|
| `laya_ask` | एक state पर टाइप किए प्रश्नों का समूह। सामान्य वाला। |
| `laya_noul` | एक हाँ/नहीं प्रश्न। `P(true)` और एक बैंड लौटाता है। |
| `laya_choice` | एक बहुविकल्पीय प्रश्न। लेबल और वितरण लौटाता है। |
| `laya_score` | एक क्रमित-पैमाने का प्रश्न। |
| `laya_plan` | «क्या यह समाएगा, और क्या कटेगा?» — बिना forward pass। |

हर विवरण बताता है कि उपकरण किस लिए *नहीं* है। जिस निर्णय मॉडल से गद्य लिखने को कहा जाए वह कुछ उपयोगी नहीं देता, और जो agent यह नहीं जानता वह प्रयास करता रहेगा।

## HTTP

```bash
laya-mcp serve --model english --port 8787
curl -s localhost:8787/health
curl -s localhost:8787/ask -H 'content-type: application/json' -d '{
  "state": {"subject": "Duplicate charge", "body": "Billed twice. Refund or we cancel."},
  "questions": {
    "churn": {"type": "noul", "instructions": "Does the user threaten to cancel?"},
    "team":  {"type": "choice", "instructions": "Which team?",
              "criteria": {"billing": "invoices, refunds", "tech": "bugs, outages"}}
  }
}'
```

`GET /health`, `GET /capabilities`, `GET /version`, `POST /ask`, `POST /plan`, `DELETE /model`। डिफ़ॉल्ट रूप से केवल loopback; कहीं और bind करने पर ज़ोरदार चेतावनी आती है, क्योंकि कोई प्रमाणीकरण नहीं है।

`POST /plan` वही body लेता है जो `/ask` लेता है और वही `budget` ब्लॉक लौटाता है जो `/ask` रिपोर्ट करता है, उसी `plan_questions` कॉल से गणना करके — बिना forward pass। इसी तरह एक क्लाइंट उत्तर के लिए कीमत चुकाने से पहले पूछ सकता है «क्या यह कटेगा?»। ठंडे host पर यह मॉडल *लोड* चुकाता है, जो अनुमान से अलग बात है।

| फ़्लैग | क्यों |
|---|---|
| `--head-max-len` | शुरुआत में बढ़ाया गया, यह उच्च-कार्डिनैलिटी `choice` का समाधान है। विकल्प इसे साझा करते हैं, इसलिए हर लेबल को अधिक जगह देना ही उन्हें अलग-अलग रखने का एकमात्र तरीक़ा है। हर कॉल पर नए सिरे से पढ़ा जाता है, इसलिए एक बार सेट करना पर्याप्त है। |
| `--max-len` | कुल बजट। इसे बढ़ाना कटे हुए state का समाधान है। |
| `--truncate-left` | बड़े state का **अंत** रखें, शुरुआत नहीं। डिफ़ॉल्ट रूप से बंद, क्योंकि यह बदल देता है कि मॉडल लंबे दस्तावेज़ का कौन-सा हिस्सा पढ़ता है — और यह उत्तर तय करता है: एक ही 16958-अक्षर के state में (आगे नक़ली कोड, पीछे सुधार) शुरुआत रखने पर `noul` **0.0706** और अंत रखने पर **0.8341** आया। जब उत्तर अंत में हो (कोई थ्रेड, लॉग, अनुबंध की अंतिम शर्तें) तब इसका उपयोग करें, और `truncated.state.kept` पढ़कर देखें कि कौन-सा सिरा बचा। |
| `--concurrency` | तभी बढ़ाएँ जब आप जानते हों कि Laya डिवाइस स्थिति साझा नहीं कर रहा। डिफ़ॉल्ट 1 सावधानी नहीं, शुद्धता है। |
| `--sidecar` | `laya-mcp mcp` को चल रहे `serve` की ओर इंगित करें। दृढ़ता से अनुशंसित: एक harness प्रति सत्र एक stdio सर्वर बनाता है, और हर एक में मॉडल रखने पर प्रति सत्र लोड लागत चुकानी पड़ती है। |

## यह क्या ठीक नहीं करता

अपस्ट्रीम के स्वयं के आँकड़े दोहराने योग्य हैं, क्योंकि जो एकीकरण परत इसके विपरीत संकेत देती है वह आपसे झूठ बोल रही है।

* **आधार checkpoints टाइप किए निर्णयों पर zero-shot में संयोग के क़रीब हैं** — अंग्रेज़ी के लिए 0.362, जबकि **बहुसंख्यक-वर्ग आधार रेखा 0.461** है। सबसे सामान्य उत्तर का अनुमान मॉडल को हरा देता है।
* **`score` सबसे कमज़ोर primitive है।** पाँच-स्तरीय क्रमित कार्य पर स्वतंत्र रूप से 35% मापा गया, जबकि Jev का 70%।
* **अंशशोधन के लिए लेबल किया डेटा चाहिए।** कच्चा ECE अंग्रेज़ी के लिए 0.466 और बहुभाषी के लिए 0.314 है, जो फ़िट करने के बाद 0.081 और 0.106 तक सुधरता है। तापमान गढ़ा नहीं जा सकता; यह पैकेज ऐसा दिखावा नहीं करेगा। जो फ़िट अपनी खोज-ग्रिड के किनारे से टकराता है, उसे तापमान के रूप में लौटाने के बजाय `saturated_buckets` में एक सीमा के रूप में दर्ज किया जाता है — क्योंकि सीमा नमूने का बयान है, मॉडल का नहीं।
* **स्थिति-पूर्वाग्रह वास्तविक है।** एक प्रकाशित fixture रन ने 50 बहुविकल्पीय मदों में से 46 में «A» चुना।
* **~20 विकल्पों से ऊपर सटीकता गिरती है**, लेखक के अनुसार।

अंशशोधन प्रायिकता को *ईमानदार* बनाता है; यह मॉडल को *सही* नहीं बना सकता। यदि आपके कार्य के लिए सटीकता वहाँ नहीं है, तो अपने क्षेत्र के डेटा पर फ़िट करें या इसे तैनात न करें।

## सत्यापन

```bash
python tests/smoke_pure.py         # 94 जाँचें: सत्यापन, योजना, अंशशोधन, त्रुटियाँ
python tests/install_harnesses.py  # 38: हर harness बोली, एक अस्थायी निर्देशिका में
python tests/mcp_protocol.py       # sidecar के साथ 37 (उसके बिना 32): वास्तविक MCP handshake और वास्तविक tool calls
python tests/stdio_latency.py      # handshake <5 सेकंड, tools/list तत्काल, tools/call उत्तर देता है
python tests/language_probe.py     # हर checkpoint प्रति भाषा वास्तव में क्या कर सकता है
laya-mcp doctor                    # क्या स्थापित है, और GPU वास्तव में क्या कर सकता है
```

तीन suites में 169 जाँचें, और हर एक ऐसी परत ढकती है जहाँ बाक़ी नहीं पहुँचतीं। `stdio_latency.py` और `language_probe.py` को मॉडल चाहिए और वे मापन हैं, अभिकथन नहीं, इसलिए वे हाथ से चलाए जाते हैं और उनके आँकड़े ऊपर उद्धृत हैं।

`smoke_pure.py` को torch, मॉडल, नेटवर्क या harness कॉन्फ़िग की आवश्यकता नहीं। `install_harnesses.py` हर harness को अस्थायी निर्देशिका में पुनर्निर्देशित करता है, क्योंकि `~/.claude.json` इतिहास और प्रति-प्रोजेक्ट स्थिति रखने वाली बड़ी साझा फ़ाइल है और उसे मिटाने वाला परीक्षण अपनी पकड़ी जा सकने वाली किसी भी त्रुटि से बुरा होगा।

`mcp_protocol.py` सबसे महत्वपूर्ण है और सबसे लंबे समय तक अनुपस्थित रहा। यह सर्वर को ठीक वैसे ही शुरू करता है जैसे harness करता है (`python -m laya_mcp mcp`), आधिकारिक SDK के साथ वास्तविक `initialize` handshake करता है, उपकरणों की सूची लेता है और उन्हें कॉल करता है। दो वास्तविक दोष बाक़ी suites से बच निकले और केवल यहीं पकड़े गए: mcp 1.30 में `FastMCP` कोई `version` आर्ग्युमेंट नहीं लेता, इसलिए सर्वर शुरू ही नहीं होता था; और टोकन-बजट चेतावनी DSH plugin के उपकरण विवरण में लिखी थी पर इस सर्वर के विवरण में कभी नहीं, इसलिए MCP इस्तेमाल करने वाला क्लाइंट यह जान ही नहीं सकता था कि बड़ा state अंत से काटा जाता है।

इसके बाद स्वीकृति इस बात से सत्यापित की गई कि harnesses इस उपकरण द्वारा लिखी फ़ाइलों को पढ़ें **और उनसे जुड़ें** — यही एकमात्र परीक्षण है जो लिखी गई फ़ाइल को स्वीकृत फ़ाइल से अलग करता है:

| harness | कैसे | परिणाम |
|---|---|---|
| opencode | `opencode mcp list` | ✓ connected |
| claude | `claude mcp list` | √ Connected |
| codex | `codex mcp list --json` | `enabled`, `"type": "stdio"`, सही argv — `auth_status: unsupported` कोई दोष नहीं: स्थानीय stdio सर्वर को प्रमाणीकरण नहीं चाहिए |
| OpenClaw | `openclaw mcp list --json` | सर्वर और stdio ट्रांसपोर्ट रिपोर्ट करता है |
| Hermes | `hermes mcp list` | ✓ enabled, और `hermes mcp test laya` जुड़कर पाँचों उपकरण ढूँढता है |
| `pi` | — | मूल MCP समर्थन नहीं; `install` इसे पहचानकर बता देता है |

यह इंस्टॉलर जिन सभी harnesses का समर्थन करता है, वे अब अपने ही औज़ारों से पुष्टि
करते हैं। यही एकमात्र जाँच है जो लिखी गई फ़ाइल को स्वीकृत फ़ाइल से अलग करती है, और
इसने अपनी जगह कमाई है: Windows पर Hermes अपना कॉन्फ़िग `~/.hermes` से नहीं,
`%LOCALAPPDATA%\hermes` से पढ़ता है, इसलिए इंस्टॉलर सफलता बताता रहा जबकि वह ऐसी
फ़ाइल लिख रहा था जिसे कोई नहीं पढ़ता। दो दोष इसे छिपाए हुए थे: Hermes को
असत्यापनीय चिह्नित किया गया था, और Windows पर इनमें से कोई lister चल ही नहीं सकता
था, क्योंकि npm हर एक को `.cmd` शिम के रूप में देता है जिसे `CreateProcess` चलाने से
इनकार करता है।

यही तालिका `stdio_latency.py` के होने का कारण है। ऊपर का हर harness एक MCP सर्वर को `initialize` पूरा करने के लिए 30 सेकंड देता है, और checkpoint लोड करने के बाद handshake का उत्तर देना बिना प्रतिस्पर्धा 19 सेकंड और GPU पर दूसरा मॉडल होने पर 275 सेकंड लेता था — इसलिए उन सबने ऐसी कॉन्फ़िग पर «Failed to connect» रिपोर्ट किया जिसे उन्होंने बिल्कुल ठीक पढ़ा था। अब लोड handshake के पीछे चलता है।
